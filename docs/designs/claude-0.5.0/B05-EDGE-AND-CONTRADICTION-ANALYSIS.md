## BD01 — written native transport handoff

**Authority and disposition.** The first ruling (delivery-b21e9f340affb6c3305885967ae8512b) suggested `accepted` for a completed native write. Fable explicitly withdrew that wording in delivery-a075e3efdd062999c6ff5844d69451db after comparison with L08 and the roadmap. This amendment uses **`written`**. `accepted` remains reserved for a carrier that undertakes retention; it is not added to the current delivery enum by BD01. No further search or native probe for a stronger interactive receipt is required.

Exact stamped wire wording:

> `written` means the integration completed one local transport write of the complete frame addressed to the native session captured for that delivery, using that session's product-owned carrier, with no explicit transport/native error observed before the result was emitted. It acknowledges only the local write. It does not assert that the native process parsed the frame, accepted its session ID, scheduled or retained the message, presented it, or consumed it. A native EOF without response bytes adds no acknowledgment. Absence of an observed rejection is not proof of acceptance.
>
> `injected` remains reserved for an identity-bound native admission acknowledgment. `queued_for_next_turn` remains reserved for a demonstrated native staging/replay primitive for a later explicit run; a completed local write alone does not qualify. Evidence of a later run's consumption may prove that tested staging path; it does not turn a future run into a fact at receipt time. `accepted` is reserved for an explicit retention undertaking and is not an alias of `written`.
>
> The Claude interactive integration returns `written` at that local completion boundary. It preserves the captured native session ID and frame contents across asynchronous work; a later identity report never retargets the frame. A native-adapter `rejected` result requires an observed native refusal or a failure before any native submission, with a reason that identifies that boundary. An uncertain write or post-submission transport loss must not be represented as a native refusal or proof of non-consumption.

The existing daemon's routing/connection failures remain their existing failures. A `rejected/not_connected` generated by the daemon is a connection observation, not evidence that Claude refused or did not consume a frame. If the native callback loses the transport after possible submission, its kit/connection failure mapping must preserve that uncertainty; do not throw into the kit's generic `rejected` mapping and describe its reason as native refusal. The bus unit must test this failure path with its exact public kit behavior before the Claude consumer uses it. This is not a new native receipt probe, a retry, or a replay mechanism.

**Roadmap comparison.** The [provided roadmap memory copy](../sources/owner-roadmap/what-agents-actually-need.md) item1 defines accepted as someone taking responsibility to retain until handoff, and explicitly requires truthful refusal when that promise cannot be made. Its stage B1 introduces retained mail later. Item6's preference for accepted/failed rather than sender-visible steering is a destination preference, not evidence that today's native socket retains anything. The [repo end goal at707d9a4](../sources/owner-roadmap/END-GOAL-707d9a4.md) independently says accepted survives receiver absence, nothing silently drops, and the page does not alter a signed wire contract. Thus `written` is a truthful narrower current-contract amendment, not fulfillment of B1 retained mail or the final mailbox interface. Current receipt projection stays explicit; it is not relabeled as a read receipt or hidden behind `accepted`.

The two supplied memory documents have SHA256 `e41de2ccea4138fd674acb4cf3970f333c9261c30e32b7bb885854de9c51f886` and `d9bac8979475a5ecfafe625e035dcae977a429a477ebe9985edb67672ee1a368`. [Provenance](../sources/owner-roadmap/SOURCE.json) distinguishes those relayed copies from the independently read repository document; the original roadmap artifact was not independently authenticated by this review.

**Exact wire unit.** Add `written` to both closed disposition enums in `bus/sdk/go/protocol/session.schema.json`: `DeliveryReceipt` and `MessageSendDelivery`. Preserve existing non-rejected fields: sender-side `session_id` and `delivery_id` are required, `reason` absent. Update the public Go/JS kit schema and fixtures, daemon/federation round-trip tests, and documented delivery meanings together. Both native-to-daemon and daemon-to-caller validation must accept the new value. No new method, message queue, persistence layer, receipt poll, native callback listener or adapter retry is introduced. Release compatible public kits/daemon before enabling the Claude `written` callback, including caller-side and federated readers of the result. Both existing enums are closed, so this is not backward-compatible with an old validator merely because the protocol number is unchanged. The bus unit must define its coordinated upgrade/version policy. An older validator rejecting it is an incompatibility, not a reason to fall back to `injected`.

Test the bus unit with complete local write, explicit pre-write failure, observed native refusal, partial/uncertain write failure, native EOF without an acknowledgment, and delivery during identity replacement. Verify remote source/target IDs and the `written` disposition round-trip unchanged. A wrong-session native frame can also have a completed write: L08 is precisely why `written` cannot claim native target admission. Do not repeat L08 merely to prove that limit again.

**Row accounting.** Mark the P05/A09 *requirement for a stronger native success receipt on the interactive carrier* **resolved by contract, BD01**. The source lead `peer_message_status` is future optional stronger evidence, not a release prerequisite. Do not mark the whole P05/A09 product/installed rows green: exact carrier/target/source binding, lane no-unrequested-work behavior, active/held/terminal ordering, UUID/replay association and next-run duplication checks remain their existing behavior/acceptance obligations. L09 proves one idle append/replay/next-run case; L10's circular harness and L15's held/release observation are not retrospectively made complete. `queued_for_next_turn` for a lane still requires its demonstrated native replay boundary; BD01 does not certify a lane queue or add one.

## BC01 — interrupt acknowledgment contradiction, accepted reconciliation

The signed protocol's `turn.interrupt` section says the empty result means the native product accepted the interrupt. Its callback-error table instead mandates an empty result after a callback error, with a quoted stderr diagnostic; its coalescing rule also allows subsequent empty replies before the first native interrupt completes. The inspected JS Worker implements those latter rules. Native acceptance cannot truthfully be inferred from every `{}` under that contract.

Proposed wording:

> A successful turn.interrupt RPC records or coalesces the interrupt request for the outstanding run. Its empty result does not certify native acceptance or completion. The worker invokes the native primitive at most once for that run. Native callback errors remain the prescribed quoted diagnostic; only the native run terminal supplies the stopping outcome. Idle remains not_running.

This explicit semantic amendment was accepted by delivery-b21e9f340affb6c3305885967ae8512b; it is not an implicit exception granted by choosing an SDK. It changes no method or schema and does not weaken message.deliver receipts. The A10 wording conflict is resolved by that acceptance; actual native lifecycle and candidate conformance remain unfulfilled until tested. An alternative stronger native-acceptance contract would require a separately designed bus-kit change; the Claude wrapper will not reproduce worker state to conceal the contradiction. Closing a connection after one callback fails cannot retract a prior coalesced reply, so that is not a solution either.

Select existing Worker callbacks subject to this named requirement gate. This removes the custom dispatch proposal and keeps native/product policy on its own side. Earlier R4 native interrupt and L11 result evidence remain positive, but neither proves an empty reply can acknowledge a failed native request.
